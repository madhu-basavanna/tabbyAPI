# Monitoring with MLflow

TabbyAPI can export **MLflow traces** of everything that happens inside the
server, so you can inspect generations and tool calls in the MLflow UI instead
of only reading console logs.

Every generation request becomes one MLflow **trace** with nested **spans**:

- **`chat.completions` / `completions` / `kobold.generate`** — the API request.
  Inputs are the request payload (messages, tools, sampling params); outputs are
  the response (content, reasoning, tool calls, usage).
- **`exllama.generate`** — the ExllamaV3 generation step. Carries the internal
  metrics: prompt tokens, cached tokens, prefill/decode times, tokens/sec,
  queue time, speculative-decoding accept/reject, and the finish reason.
- **`parse.toolcalls`** — one span per tool-call parse, with the tool names and
  the full parsed arguments.

> [!NOTE]
> Tracing is **opt-in** and **optional**. `mlflow` is not a hard dependency.
> When it is disabled (the default) the tracing code is a no-op and the server
> behaves exactly as before.

## Setup

1. Install the optional `mlflow` package:

   ```bash
   pip install 'mlflow>=3.0'
   # or, as a tabbyAPI extra:
   pip install '.[monitoring]'
   ```

2. Add a `monitoring` section to `config.yml`:

   ```yml
   monitoring:
     mlflow: true
     # A local SQLite file, or a hosted MLflow server (http://localhost:5000)
     mlflow_tracking_uri: sqlite:///mlflow.db
     mlflow_experiment: tabbyapi
   ```

3. Restart the server. When tracing is active you'll see a startup line:

   ```
   INFO: MLflow tracing enabled (experiment 'tabbyapi', tracking uri sqlite:///mlflow.db)
   ```

## Viewing traces

Start the MLflow UI against the same tracking backend:

```bash
mlflow ui --backend-store-uri sqlite:///mlflow.db --host 127.0.0.1 --port 5001
```

Then open `http://127.0.0.1:5001` and select the `tabbyapi` experiment. Each
request is a trace; expand it to see the generation metrics and each parsed
tool call.

> [!TIP]
> Point `mlflow_tracking_uri` at a hosted MLflow server (e.g. Databricks or a
> self-hosted `mlflow server`) to centralize traces from multiple TabbyAPI
> instances.

## Configuration

| Option                  | Default               | Description                                                              |
| ----------------------- | --------------------- | ------------------------------------------------------------------------ |
| `mlflow`                | `false`               | Enable MLflow tracing. Requires the `mlflow` package.                    |
| `mlflow_tracking_uri`   | `sqlite:///mlflow.db` | Tracking backend: a local SQLite file or a hosted MLflow server URL.     |
| `mlflow_experiment`     | `tabbyapi`            | Name of the experiment traces are written to.                            |

## Privacy

Traces store the **full request and response payloads**, including prompts,
messages, and tool-call arguments, in the tracking backend. Treat the tracking
store as sensitive data. This is the same privacy consideration as the
`logging.log_chat_completion_requests` option.
